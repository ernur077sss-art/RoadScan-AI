# Этапы 3 и 7: внешние подключения

## Бесплатный вход

По умолчанию `ROADSCAN_AUTH_MODE=password`: телефон служит логином, пароль хранится как salted scrypt hash (N=32768, r=8, p=3). Номер и личность не верифицируются, SMS не отправляются. По решению владельца регистрация жителя по умолчанию принимает PIN ровно из 4 ASCII-цифр; доступен и длинный пароль от 15 до 128 символов. Ведущие нули сохраняются, пробелы не обрезаются. Для обеих форм требуется согласие.

Профиль `scrypt-pin:32768:8:3` отмечает короткий PIN в хеше. Прежний `scrypt:32768:8:3` совместим с существующими длинными паролями. PIN-аккаунту нельзя назначить роль инспектора/администратора через API или CLI; сервер также отклоняет вход и сессию такого аккаунта при ошибочном назначении роли напрямую в БД. Для сотрудника при регистрации нужно выбрать длинный пароль. Изменение забытого пароля/переход существующего PIN-аккаунта на длинный пароль пока не реализованы.

Лимиты сохраняются в БД: 5 попыток на нормализованный номер за 15 минут, 20 за сутки, 30 на IP за 15 минут; регистрация дополнительно ограничена 10 в час на IP. В лимит номера входят регистрация и успешные входы. Старый OTP-аккаунт нельзя перехватить повторной регистрацией. Четырёхзначный PIN имеет только 10 000 вариантов: ограничения уменьшают онлайн-перебор, но не делают его равноценным длинному паролю при утечке хешей. Это осознанное упрощение тестового сервиса по запросу владельца. Нельзя сбрасывать пароль по одному заявленному номеру.

## SMS — необязательный, отключённый режим

Только при `ROADSCAN_AUTH_MODE=otp`: `ROADSCAN_SMS_MODE=development` возвращает случайный код **только в локальном dev/test режиме**. Это не отправка SMS. Production с OTP требует реальный HTTPS bridge. В режиме `password` оба OTP-эндпоинта отключены, и наличие SMS bridge не требуется.

Bridge — наш внутренний контракт адаптера, **не заявленный API какого-либо провайдера**. Оператор выбирает SMS-провайдера и реализует мост, либо адаптирует transport в api/main.py по его документации:

POST ROADSCAN_SMS_URL, Authorization: Bearer ROADSCAN_SMS_TOKEN.
JSON: {phone, text, request_id}. Ответ 2xx и {accepted:true} означают принятие SMS-провайдером; доставка на телефон отдельно не доказана. Секреты только в окружении. Предусмотреть идемпотентность request_id у моста. Пользовательский ввод не определяет адрес назначения HTTP.

## 109
Режимы: disabled (по умолчанию), simulator (только dev/test).
Симулятор создаёт outbox в транзакции подтверждения, worker выдаёт только status=simulated и номер DEMO-109-*. Реальной отправки нет. Production запрещает симулятор.

До реализации реального адаптера нужны: документация 109 Семея, тестовый доступ, обязательные поля и требования к личности заявителя, правила авторизации, лимиты медиа, коды ошибок, внешняя идемпотентность/поиск по клиентскому ключу и статусы/вебхуки.

Реальный адаптер должен фиксировать accepted только по подтверждению 109. После сетевого таймаута с неопределённым результатом сначала сверять внешний номер по ключу, иначе повтор может создать вторую заявку. Исчерпанные повторы требуют внимания оператора. Не подставлять несуществующие URL и номера. Изменения подтверждённого объекта после внешней отправки требуют согласованного протокола обновления/отмены — текущий симулятор этого не доказывает.
